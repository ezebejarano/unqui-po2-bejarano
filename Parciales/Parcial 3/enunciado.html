Parcial de práctica N°3 · Parte práctica

(Sistema de seguimiento de pedidos — para practicar State + Observer)

Ejercicio 1

Un e-commerce necesita modelar el ciclo de vida de un Pedido. Cada pedido conoce un identificador y un cliente, y en todo momento se encuentra en un estado. Las operaciones que se le pueden pedir a un pedido son: confirmar, enviar, entregar y cancelar.

El resultado de cada operación depende del estado actual del pedido. Los estados y sus transiciones válidas son:

  • Pendiente: recién creado. Se puede confirmar (pasa a Confirmado) o cancelar (pasa a Cancelado). Enviar o entregar no está permitido.
  • Confirmado: el pago fue aceptado. Se puede enviar (pasa a Enviado) o cancelar (pasa a Cancelado). Confirmar o entregar no está permitido.
  • Enviado: ya salió del depósito. Se puede entregar (pasa a Entregado). Ya no se puede cancelar, ni confirmar ni volver a enviar.
  • Entregado: estado final. No permite ninguna operación.
  • Cancelado: estado final. No permite ninguna operación.

Cuando una operación no está permitida en el estado actual, se debe lanzar una excepción con un mensaje claro (por ejemplo throw new RuntimeException("No se puede enviar un pedido que no fue confirmado")). El diseño debe permitir incorporar nuevos estados en el futuro sin tener que modificar los estados ya existentes.

Ejercicio 2

Los pedidos deben poder ser seguidos por distintos interesados. Cada vez que un pedido cambia de estado, debe notificar automáticamente a todos los interesados que se hayan suscripto a él, para que reaccionen como quieran (por ejemplo: mandar un mail al cliente, avisar al sistema de logística, registrar en una auditoría).

Para ello se dispone de la siguiente interfaz externa, la cual puede utilizar y no debe implementar:

public interface ObservadorDePedido {
    // Se invoca cada vez que el pedido cambia de estado.
    public void seActualizo(Pedido pedido);
}

El pedido debe permitir suscribir y desuscribir observadores. Cada vez que una operación del Ejercicio 1 provoca un cambio de estado, se debe avisar a todos los observadores suscriptos. Un observador que se dio de baja ya no debe recibir avisos.

Actividades

  1. Genere un diagrama de clases UML con las soluciones completas e integradas de ambos ejercicios.
  2. Indique los patrones de diseño utilizados, incluyendo los roles que cumplen sus clases siguiendo las definiciones de Gamma et. al.
  3. Implemente en Java la funcionalidad completa para resolver todos los requerimientos y las clases necesarias. Incluya los constructores. Implemente solamente los accessors que necesite.
  4. Codifique un ejemplo de instanciación: cree un pedido, suscríbale al menos un observador, y hacélo pasar por la secuencia Pendiente → Confirmado → Enviado → Entregado, mostrando que en cada cambio los observadores son avisados. Intente además una operación inválida (por ejemplo, entregar un pedido recién creado) para ver que lanza la excepción.
